02 · 核心价值

Northstar 的价值在于让每次讨论形成可承接的产物，让每次执行留下可以核对的结果，让遇到问题的人知道该把工作交给谁。

上下文可以被承接

当 PM 完成需求、Dev 接手设计时，上游文档、未解决问题和待办都属于同一个需求。接手者能知道当前依据是什么、有哪些阻塞，以及现在应该处理哪项工作。

角色切换恢复的是当前需求对应的工作，而不是让模型凭一段聊天摘要猜测进度。每个角色的待办分开保存，产品问题、实现任务与质量问题各有归属。

角色主要责任与产物
PM · 产品目标用户、业务规则、需求范围与验收方向；调研发现、PRD 和产品签核。
Dev · 技术技术方案、影响范围与实现；技术调研、TD、代码候选和验证结果。
QA · 质量测试覆盖、缺陷与质量判断；测试计划、用例、执行依据和复测结论。

业务问题有明确决策归属

技术设计遇到“重复素材是否应该自动合并”这类业务问题时，Dev 可以提出异议，交给 PM 确认规则。PM 决策或修订 PRD 后，Dev 再更新 TD 与实现计划。

这样，技术判断和产品判断可以各自负责。讨论中产生的新规则有明确的确认过程，相关设计也会随着产品决策重新对齐。

“评审通过”与当前版本对应

文档曾经通过评审，并不代表修改后的版本仍然满足原结论。Northstar 将语义评审与被评产物、上游输入和评审规则的版本绑定；这些依据变化后，旧结论需要重新核对。

例如 PRD 新增一条约束，TD 就需要检查方案是否仍然适用。签核时，系统会重新读取当前事实，核验有效评审与待解决问题。

执行结果可以核实

工具调用记录、文件变化、审批决定和验证结果共同构成执行依据。用户可以查看实际改了什么、哪些命令成功、哪里失败，以及下一步需要补充什么。

文件写入还有落地校验。如果工具声称成功，却没有产生预期变化，这个异常会进入后续处理。独立验收则检查编码候选是否通过确认过的命令，而不只采用执行 Agent 的总结。

返工成为流程的一部分

产品异议进入 PM 待确认，技术问题由 Dev 处理，缺陷形成 Dev 修复待办并交回 QA 复测。流程允许返回前一阶段，让修改有对应的责任与关闭依据。

发生中断时，已经记录的结果、待处理问题和可续接操作能继续被检查。方向变化时，可以使用恢复点或需求分支回滚调整现场。

扩展能力保持相同的边界

模型适配、Skill 和 MCP 提供不同层次的扩展：模型负责理解和生成，Skill 提供工作方法，工具负责接触文件与外部能力。扩展后的操作仍需要符合当前权限和执行策略。

这让能力接入与产品流程保持联系。后续章节会进一步解释 流程治理、版本一致性 和 扩展架构 的技术机制。
